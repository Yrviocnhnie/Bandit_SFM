## Executive Summary

We extended the phase-1 online-learning setup to **phase 2**, where the same
scenario can contain **multiple feedback anchors**.

Base model:

- `NeuralEncoder LinUCB`
- offline artifact: `v6_2k_neural_linear_3p3a_hardneg_other_stratified_split`

Online update scope:

- freeze the neural encoder
- update only the per-action disjoint LinUCB heads

Phase-2 goal:

- allow different contexts inside the same scenario to prefer different actions
- use both `like` and `dislike` feedback
- keep the update local rather than globally rewriting the whole scenario

Final phase-2 result:

- best phase-2 mode: `hard-assigned-local-balanced`
- anchor success: `16 / 18`
- zero-neighbor anchors: `0`
- average effective neighbors per feedback item: `707.3`

Compared with the original phase-2 hard assignment:

- success improved from `12 / 18` to `16 / 18`
- zero-neighbor anchors dropped from `6` to `0`

## 1. Goal And Why It Matters

Phase 1 only showed that a single feedback anchor can locally personalize the
ranking.

Phase 2 asks the product-relevant question:

> If the user gives different feedback on different contexts within the same
> scenario, can the model learn different local preferences?

This matters because a real scenario is not homogeneous. For example:

- one `OFFICE_LUNCH_OUT` context may prefer `O_SHOW_PAYMENT_QR`
- another `OFFICE_LUNCH_OUT` context may prefer `R_ENJOY_LEISURE_MOMENT`

Phase 2 is the first test of whether the online-learning mechanism can support
that kind of within-scenario personalization.

## 2. Base Model

Base model:

- `NeuralEncoder LinUCB`
- offline artifact: `v6_2k_neural_linear_3p3a_hardneg_other_stratified_split`

Online update scope:

- freeze the neural encoder
- update only the per-action disjoint LinUCB heads

This preserves the stable offline latent space while allowing light online
personalization through the UCB heads.

## 3. Method

We reused the same core design from phase 1:

- frozen neural encoder
- online updates only to the disjoint LinUCB heads
- margin-aware reward selection

The key phase-2 change was the **neighbor allocation mode**.

Original phase-2 mode:

- `hard-assigned-local-cutoff`
- failure mode: some anchors received no owned neighbors

Final phase-2 mode:

- `hard-assigned-local-balanced`
- parameters:
  - `min_neighbors = 500`
  - `max_neighbors = 2000`
  - `similarity_threshold = 0.80`

Balanced allocation works in two stages:

1. each anchor first receives a minimum support floor
2. the remaining same-scenario contexts are distributed locally, up to the max cap

This keeps the update local while preventing anchor starvation.

Reward policy remained:

- `margin-aware-fixed-radius-v1`

## 6. Interpretation

The phase-2 result is strong enough to support the main claim:

> The same scenario can now contain multiple local preference anchors, and the
> model can learn different action ordering in different parts of that scenario.

Three especially useful examples:

1. `OFFICE_LUNCH_OUT / Context A`
   - `O_SHOW_PAYMENT_QR` moved `3 -> 1`
   - `R_MEAL_BREAK` moved `2 -> 46`

2. `OFFICE_LUNCH_OUT / Context B`
   - `R_ENJOY_LEISURE_MOMENT` moved `6 -> 3`
   - this is the clearest out-of-top3 like success case

3. `CAFE_QUIET / Context B`
   - `O_TURN_ON_SILENT_MODE` moved `3 -> 1`
   - `R_DEEP_WORK_WINDOW` moved `2 -> 3`

These are exactly the kinds of local behavior we wanted phase 2 to show.

## 7. Comparison With The Original Phase-2 Mode

Original phase-2 mode:

- `hard-assigned-local-cutoff`

Final phase-2 mode:

- `hard-assigned-local-balanced`

Comparison:

| metric | original | balanced |
| --- | ---: | ---: |
| anchor success | `12 / 18` | `16 / 18` |
| zero-neighbor anchors | `6` | `0` |
| avg effective N | `707.3` | `707.3` |
| aligned anchor rank movement | `+7.11` | `+8.33` |
| aligned anchor score movement | `+0.491` | `+0.560` |
| aligned same-scenario rank movement | `+6.80` | `+9.86` |
| aligned same-scenario score movement | `+0.510` | `+0.604` |

Important point:

- the improvement did **not** come from using more neighbors overall
- it came from distributing neighbors more evenly across anchors

This is why balanced local allocation is the better phase-2 default.

## 10. Recommendation

Use `hard-assigned-local-balanced` as the new phase-2 baseline:

- propagation mode: `hard-assigned-local-balanced`
- `min_neighbors = 500`
- `max_neighbors = 2000`
- `similarity_threshold = 0.80`
- reward policy: `margin-aware-fixed-radius-v1`

This preserves the stability of the frozen-encoder online update design while
making multi-anchor same-scenario personalization much more robust.
